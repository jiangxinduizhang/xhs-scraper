# 07 - 开盘啦迁移方案

## 背景

目标不是继续扩展小红书采集能力，而是基于当前仓库的三层架构，验证是否可以迁移到另一个 Android App：

- `uiautomator2` 负责 UI 控制
- `mitmproxy` 负责 HTTPS 数据拦截
- `Midscene` 负责异常兜底
- SQLite 负责落库与导出

当前仓库的实现是小红书定制版，迁移到“开盘啦”时，**通用框架可复用，业务适配必须重做**。

## 最初诉求

1. 判断“开盘啦”是否可以被当前方案采集
2. 先验证最小闭环，而不是一开始全量重构
3. 让开发、验证、复盘都可追踪，避免会话结束后丢上下文
4. 保留原仓库主线，独立分支迭代

## 当前分工

- Windows：主要负责写代码、改文档、提交分支
- Mac mini：负责真实运行、连手机、抓包、验证

## 需要长期记住的注意点

1. 不要把小红书的页面文本、host、path、包名直接迁移到新 App。
2. 不要先大改框架，先做最小验证闭环。
3. 不要假设“开盘啦”一定能被代理抓到，先验证是否存在证书校验、加密或 WebSocket。
4. 不要用 Wi-Fi 代理替代 USB tunnel，本项目默认走 `adb reverse`。
5. 不要在 Windows 上假设脚本可直接运行，最终验证放到 Mac mini。
6. 不要在没有抓包证据前写死解析规则，解析器必须跟实测响应对齐。
7. 不要动 `main` 主线，所有试验都在 `dev-kpl` 分支。

## 方案总览

### 保留

- `src/orchestrator.py` 的调度模式
- `src/storage/db.py` 的数据落库模式
- `src/proxy/addon.py` 的拦截入口结构
- `src/controller/device.py` 的设备连接与预检思路
- `src/midscene/bridge.py` 的 Python -> Node 调用方式

### 重写

- `src/config.py`
- `src/proxy/parser.py`
- `src/controller/state.py`
- `src/controller/actions.py`
- Midscene prompt 与页面语义

### 先不碰

- 原始小红书解析测试
- 原有采集逻辑的完整行为链
- 复杂的数据导出格式

## 迁移路径

### 第 0 阶段：环境确认

目标：确认 Mac mini 能作为执行机跑起来。

检查项：

- `git` 能拉到 `dev-kpl`
- `adb` 能识别已 root 手机
- `adb reverse` 可用
- `mitmdump` 可启动
- `uiautomator2` 可连接设备
- Node.js 可被 Midscene 调用

通过标准：

- 设备能连上
- 代理端口能监听
- 手机能正常上网
- 代码可从 Mac mini 运行到最小调试链路

### 第 1 阶段：目标 App 画像

目标：先搞清“开盘啦”属于哪种应用形态。

要确认的内容：

- 包名
- 主页面类型
- 是否原生列表页
- 是否 WebView / 图表页占比高
- 是否存在明显资讯流、行情流、资金流、社区内容

结果分支：

- 如果是公开资讯 + 列表页为主，UI + 抓包可行性较高
- 如果是实时行情 + WebSocket 为主，解析复杂度显著上升
- 如果证书绑定强、接口加密重，代理层可行性下降

### 第 2 阶段：抓包验证

目标：确认有没有可以直接消费的结构化数据。

验证问题：

- 能不能看到 HTTP/HTTPS 请求
- 是否返回 JSON
- 关键数据是否在普通接口里
- 是否需要处理加密 payload
- 是否只看到空壳接口或聚合接口

通过标准：

- 至少拿到一批稳定接口样本
- 能识别 1 类可落库数据

### 第 3 阶段：UI 验证

目标：确认能否稳定控制页面流转。

验证问题：

- 首页是否可识别
- 目标列表页是否可定位
- 返回逻辑是否稳定
- 是否存在弹窗、引导、验证码

通过标准：

- 能从首页进入目标页
- 能从目标页返回
- 不依赖一次性脆弱坐标

### 第 4 阶段：最小闭环

目标：从“启动 App”到“抓到一小批数据并落库”闭环跑通。

最小闭环定义：

1. 启动 App
2. 进入一个固定目标页面
3. 触发至少一个数据请求
4. 拦截并解析
5. 保存到 SQLite
6. 导出文件可读

通过标准：

- 数据库中能看到新增记录
- 原始响应可追溯
- 导出文件字段不空

### 第 5 阶段：扩展

目标：在最小闭环稳定后，再扩数据面。

可扩展方向：

- 更多栏目
- 更多页面状态
- 更多字段
- 更完整的导出格式
- 更稳的异常处理

## 实施顺序

1. Mac mini 环境验证
2. App 画像与请求观察
3. 只改 `config` 和最小适配层
4. 做一个 endpoint 到 parser 的样例
5. 落库成功
6. 再补 UI 路径
7. 再补异常兜底

## 验证思路

### 网络层

- 代理能否生效
- 能否看到真实请求
- 是否有证书校验失败
- 是否存在 WebSocket / 二进制协议

### UI 层

- 能否连上设备
- 能否识别页面
- 能否执行点击 / 滑动 / 返回
- 能否稳定回到目标页

### 数据层

- 能否把响应转成结构化记录
- 能否落库去重
- 能否导出

## 复盘模板

每次尝试都记录下面几项：

- 日期
- 分支
- Mac mini 环境状态
- 手机状态
- App 版本
- 抓包结果
- UI 控制结果
- 失败点
- 下一步动作

## 暂定判断标准

- **可行**：能稳定抓到至少一类结构化数据，且最小闭环可重复
- **部分可行**：能抓到少量公开数据，但核心数据被阻断
- **不可行**：代理和 UI 两层都被强约束，无法形成稳定闭环

它的核心不是“实现一个自动化框架”，而是“把 AI 调度抓取任务的闭环做成可持续、可复盘、可验收的长期协议”。

## 目标

把当前 `开盘啦` 采集能力整理成一个可跨 session 继续推进的闭环：

1. AI 发起任务
2. skill 产出任务意图与约束
3. script / CLI 执行抓取
4. proxy / parser / db 完成采集、解析、落库
5. report / summary 输出结果
6. AI 读取结果并决定下一步

目标不是让 AI 直接操作每个 UI 细节，而是让 AI 能稳定地“调度任务、读取结果、继续推进”。

## 最高优先级原则

这份方案里，**验收和反省标准优先于一切实现细节**。后续迭代不得偏离以下原则：

- 先验证，再扩展
- 先闭环，再优化
- 先可回读，再自动化
- 先稳定，再抽象
- 先可维护，再追求覆盖面

任何新代码、新脚本、新 skill、新流程，只要不能同时满足这些原则，就不应进入主线。

## 当前原则

- 单机优先：Mac mini 作为唯一开发与执行机
- 任务优先：先定义任务契约，再扩实现
- 结果优先：每次执行都必须留下可回读产物
- 小步闭环：先打通一条命令链，再扩展页面与字段
- 可恢复：失败时能重试、回退、重跑

## 内部建设目标

内部建设只做一件事：把抓取闭环做稳、做薄、做可复盘。

### 内部链路

1. TaskSpec 定义任务
2. Runner 执行任务
3. Proxy / Parser / DB 处理数据
4. Report / Verify 负责回读和校验
5. 通过 step_events 证明过程发生

### 内部建设原则

- runner 保持薄
- parser 只做解析
- report 只做回读
- verify 只做校验
- 任务和结果都必须落盘

## 需要补的闭环层

### 1. 任务层

定义“这次要做什么”。

建议的最小任务字段：

- `task_id`
- `app`
- `page`
- `goal`
- `success_criteria`
- `output_path`
- `retry_policy`
- `max_runtime`

### 2. 执行层

把任务稳定落成脚本调用，而不是让 AI 直接点 UI。

建议保留三个稳定入口：

- `capture`：执行一次抓取
- `verify`：检查数据是否真正进入 DB / raw
- `export`：导出可读结果

### 3. 产物层

每次执行必须输出固定产物，便于跨 session 接续：

- `data/raw/*.jsonl`
- `data/*.db`
- `reports/*.md`
- `runs/*.json`
- `logs/*.log`

### 4. 反馈层

AI 需要读取的不是“执行过程”，而是“执行结果摘要”。

建议最少包含：

- 抓到了多少条
- 命中了哪些 note_type / source
- 是否与预期页面一致
- 是否存在异常
- 下一步建议

### 5. 恢复层

失败后应能自动恢复到可继续状态。

建议支持：

- 重新拉起 App
- 重新挂代理
- 回首页
- 重新执行当前任务

## 推荐的目录约定

建议后续逐步固定这些目录：

- `docs/`：长期方案与阶段总结
- `data/raw/`：原始响应样本
- `data/`：SQLite 数据
- `reports/`：执行结果汇总
- `runs/`：每次任务的机器可读记录
- `logs/`：执行日志

## 推荐的任务契约

建议每次抓取都先生成一个最小任务文件，例如：

```json
{
  "task_id": "kpl-20260331-market-emotion",
  "app": "kaipanla",
  "page": "market_emotion",
  "goal": "验证市场情绪页可稳定抓取并落库",
  "success_criteria": [
    "能进入情绪页",
    "抓到至少 1 个真实响应",
    "数据库新增结构化记录",
    "导出结果可读"
  ],
  "output_path": "reports/kpl-20260331-market-emotion.md",
  "retry_policy": {
    "max_attempts": 2,
    "resume_from_last_state": true
  },
  "max_runtime": 1800
}
```

## 推荐的运行结果契约

建议每次执行都写一个 `runs/*.json`，至少包含：

- `task_id`
- `started_at`
- `finished_at`
- `status`
- `captured_count`
- `sources`
- `note_types`
- `db_path`
- `raw_paths`
- `error`
- `next_action`

这样 AI 在跨 session 时，只要读最新 `runs/*.json` 和 `reports/*.md` 就能继续，不依赖聊天上下文。

## 验收标准

判断这套闭环是否合格，必须同时满足下面的标准。

### A. 功能验收

- 能通过明确任务触发一次抓取
- 能稳定进入目标页面
- 能抓到真实响应
- 能解析出结构化记录
- 能写入 SQLite
- 能导出可读结果
- 能生成机器可读运行结果
- 能生成人工可读报告

### B. 稳定性验收

- 同一任务可重复执行
- 失败后可以恢复并重试
- 任务结束后环境可回到可继续状态
- 不依赖聊天上下文才能继续
- 不依赖人工记忆才能复盘

### C. 可维护性验收

- 新增页面时，不需要大改 runner 核心
- 新增任务类型时，不需要重写已有 parser
- 新增报告字段时，不需要改执行逻辑
- 关键结构有明确的数据契约
- 代码职责分明，入口薄，执行层薄

### D. 可读性验收

- 看文件名就能知道职责
- 看函数名就能知道作用
- 看报告就能知道这次做了什么
- 看 run.json 就能知道这次成功还是失败
- 任何关键决策都能追溯到文档和产物

### E. 自动化验收

- AI 只需要读任务、执行结果和报告，就能决定下一步
- AI 不需要直接理解 UI 坐标细节
- AI 不需要直接改抓取底层代码
- AI 不需要手动翻找历史聊天记录才能接着做

## 反省标准

每次迭代结束后，必须按下面的问题反省是否跑偏。

### 1. 是否过度设计

- 这次新增的抽象是不是已经被两次以上重复验证过
- 这层抽象是不是只是为了“看起来更通用”
- 这次是否提前引入了未来可能用不到的复杂机制

### 2. 是否职责混乱

- runner 是否开始承担页面细节
- parser 是否开始承担调度逻辑
- skill 是否开始介入执行细节
- report 是否开始写业务逻辑

### 3. 是否缺少可持续性

- 这次结果是否能跨 session 复用
- 这次任务是否有明确输入和输出
- 失败后是否能恢复
- 后续是否会因为上下文丢失而重做

### 4. 是否偏离目标

- 当前改动是否仍在推进“AI 可调度闭环”
- 是否只是为了局部功能好看
- 是否已经开始向“万能框架”漂移
- 是否有文件越来越像临时脚本堆

### 5. 是否可验收

- 这次改动是否有明确验收点
- 是否能用命令和产物判断成败
- 是否能用文档复盘这次为什么做、做到了什么

## 现在的推进顺序

1. 冻结当前稳定抓取能力，不再先扩页面
2. 把抓取任务封成统一 CLI
3. 让 CLI 输出机器可读的运行结果
4. 把运行结果同步成简短报告
5. 再接 skill / automation 层
6. 最后让 AI 根据报告自动决定下一步

## 任务拆分建议

### 第一阶段：命令化

目标：一条命令完成一次明确任务。

需要做到：

- 任务参数可传
- 代理可启停
- 页面可指定
- 抓取可重复
- 结果可导出

### 第二阶段：报告化

目标：每次运行后自动生成摘要。

需要做到：

- 抓到了什么
- 缺了什么
- 是否达到阈值
- 下一步是什么

### 第三阶段：AI 调度化

目标：AI 只负责挑任务和看报告。

需要做到：

- skill 输出任务意图
- 脚本执行任务
- AI 根据报告决定是否继续

### 第四阶段：自动闭环化

目标：AI 可以连续推进，不需要人工盯每一步。

需要做到：

- 自动发现失败
- 自动重试
- 自动换页面 / 换样本
- 自动记录阶段进度
